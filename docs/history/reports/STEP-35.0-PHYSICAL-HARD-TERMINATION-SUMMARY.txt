Interpretation boundary:
- This report proves a hard native/runtime/kernel termination that bypassed managed catch/finally; it explains why no normal Step-35 report was written.
- The CODESIGNING/Invalid Page text does not by itself prove the transformed managed DLL modified a signed executable page. PC=0x0 is also consistent with a null native function-pointer call/jump.
- The visible Gate-B label is not a trustworthy code frontier. Gate B is awaited from Task.Run; after it returns, the continuation resumes on the main thread and Gate C performs synchronous reflection/invocation work before its first incomplete await and before UIKit is guaranteed to repaint.
- Therefore the exact crash frontier remains B→C until durable in-process checkpoints prove otherwise.

Related fresh-process observation:
Running Step 34 and then Step 35 in the same app process causes a normal Step-35 Gate-A rejection because sts2 is already resident. This is expected and confirms the fresh-process guard; it is not the hard-crash defect.
